## ⚡ 2. What to Test with **Grafana k6** (Concurrency, Race Conditions & Stress Suite)

**Strength:** Parallel Virtual Users (VUs), synchronized barrier execution, lock-contention stress, throughput/latency (`p95`/`p99`) degradation, and race-condition detection.

| Audit Finding / Area | Specific Test Cases to Automate in k6 |
| :--- | :--- |
| **F-08: Unbounded `FAILED` Order Flooding & Pagination DoS** | • **Stage 1 (Write Flood):** 20 VUs rapidly submit invalid orders (`422 INSUFFICIENT_FUNDS` / `INSUFFICIENT_STOCK`) for 30 seconds, generating thousands of `FAILED` rows in `orders` at zero balance cost.<br>• **Stage 2 (Read Degradation):** Concurrently poll unpaginated `GET /api/admin/orders` and `GET /api/user/orders` and assert `p95 < 500ms` and memory stability (exposes OOM / latency explosion caused by missing pagination). |
| **F-10: Inventory Depletion Race (Overselling Check)** | • **50 VUs vs. Stock of 5:** 50 VUs simultaneously call `POST /api/user/orders` (`quantity: 1`) for a product with `stock_quantity: 5` and high user balance.<br>• **Assertion:** `201 Created == 5`, `422 INSUFFICIENT_STOCK == 45`, `0` `500` errors (no unhandled SQL `40001` serialization failures), final `stock_quantity == 0`, and user balance debited $5 \times \text{price}$. |
| **F-10: Balance Overdraft Race (Double-Spend Check)** | • **50 VUs vs. Balance for 3 Items:** 1 User with `balance: 300.00` fires 50 simultaneous `POST /api/user/orders` for a `\$100.00` product with `stock_quantity: 100`.<br>• **Assertion:** `201 Created == 3`, `422 INSUFFICIENT_FUNDS == 47`, final `balance == 0.00` (never negative), and `stock_quantity == 97`. |
| **F-10: Concurrent Order Cancellation Race (Double-Refund Check)** | • **20 VUs Cancelling the Same Order:** 20 Admin VUs simultaneously send `PATCH /api/admin/orders/{id}/status` (`{"status": "CANCELLED"}`) for the same `PROCESSED` order.<br>• **Assertion:** `200 OK == 1`, `422 INVALID_STATUS == 19`, customer balance is refunded **once**, and product stock is restored **once**. |
| **F-10: Cross-Transaction Deadlock Detection (`40P01` / `40001`)** | • **Multi-Actor Lock Contention:** Run 3 concurrent k6 scenarios targeting the **same `user_id` and `product_id`** simultaneously:<br>  - Scenario A (20 VUs): `POST /api/user/orders` (locks `users` + `products`)<br>  - Scenario B (10 VUs): `PATCH /api/admin/orders/{id}/status` (locks `orders` + `users` + `products`)<br>  - Scenario C (10 VUs): `POST /api/admin/users/{id}/balance/top-up` (locks `users`)<br>• **Assertion:** `http_req_failed (status >= 500) == 0` (verifies deterministic lock ordering and absence of PostgreSQL deadlocks). |
| **F-10: Lost-Update Race on `PATCH /api/admin/products/{id}/stock`** | • Admin VU updates stock via `PATCH /api/admin/products/{id}/stock` (`stock_quantity: 50`) while User VUs concurrently purchase units via `POST /api/user/orders`.<br>• Demonstrates and measures the lost-update anomaly where absolute stock assignment overwrites concurrent order decrements. |
| **BR-01: Timing Side-Channel & Bcrypt CPU Saturation** | • **Timing Oracle Check:** Compare k6 `http_req_waiting` (`p50`/`p95`) distribution on `POST /api/user/login` between an existing username (wrong password) and a non-existent username $\rightarrow$ distributions must match (validates dummy bcrypt hash in `TECH_SPEC.md` line 279).<br>• **Bcrypt Cost 12 DoS:** 50 concurrent login requests (`BcryptCost = 12` takes ~250–350ms CPU per hash) to check if login floods starve `/api/user/products` or `/api/user/orders` goroutines. |
